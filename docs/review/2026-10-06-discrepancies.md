- PARA-01: The parse-time port only seeds kubernetes.service.port when unset (kubernetes.go:387-389), a key docker/podman do not have. The port that reaches the status script is Defaults.EffectiveManagementPort() on all three platforms at generation time (gen.go:212 via deploy.ManagementPort -> deploy.go:545-547; gen.go:273; gen.go:430), so the outputs are equivalent. (see internal/spec/env.go:65-72, internal/spec/kubernetes.go:380-389, internal/gen/gen.go:212, internal/deploy/deploy.go:545-547, internal/gen/gen.go:273, internal/gen/gen.go:430)
- PARA-04: active_* modes are coordinated through the broker's management queue, so several single-container docker/podman hosts in active_standby is a legitimate topology; checkLeaderElection enforces the platform-agnostic requirements (queue, solace session) and both renderers deliberately model active_standby by withholding the static role label. The replicas check is a kubernetes-only concept (one Deployment, many copies), so it has no docker/podman analogue. (see internal/validate/validate.go:456-501, internal/dockergen/dockergen.go:115-126, internal/podmangen/podmangen.go:106-120, internal/validate/validate.go:713-717)
- PARA-06: The three delivery models are documented side by side in UG 9.3; kubernetes needs an explicit create-or-existing choice because the Secret is a cluster object the operator may own, and omitting the block produces a warning naming the consequence (validate.go:238-240). Deliberate, documented asymmetry. (see docs/userguide.md:1720-1768, internal/validate/validate.go:238-240, internal/spec/kubernetes.go:85-88, docs/userguide.md:1732-1733)
- PARA-07: A kubernetes Secret volume and a host bind mount are the only mechanisms each platform has; both land the stores at /app/external/classpath/truststores, and UG 9.3 documents both. The literal spelling of that path in deploy.go is reported under PARA-12. (see internal/gen/gen.go:587-598, internal/deploy/deploy.go:426-430, docs/userguide.md:1770-1780)
- PARA-08: UG 9.4 documents that compose has no registry-auth field and podman's secret store cannot supply pull credentials, and tells the operator to `docker login`/`podman login`. Documented platform limitation. (see docs/userguide.md:1787-1825, docs/userguide.md:1813-1820)
- PARA-09: GeneratePodman always sets StatusScriptPath (gen.go:444), so on the tool's path the quadlet HealthCmd is emitted as unconditionally as compose's; the conditional only guards direct callers. That kubernetes restarts on a failed liveness probe while docker/podman only report is stated in all three renderers and in the UG as a deliberate choice. (see internal/gen/gen.go:444, internal/deploy/deploy.go:443-445, internal/dockergen/dockergen.go:213-215, internal/podmangen/podmangen.go:189-191, docs/userguide.md:1451-1452, docs/userguide.md:1538-1540, docs/userguide.md:2231-2237)
- PARA-10: A kubernetes env value must be a YAML string, compose's environment mapping is YAML too, and systemd Environment= has no scalar typing, so the quotes follow each sink's grammar; the container receives the same string on all three. (see internal/deploy/deploy.go:403-404, internal/dockergen/dockergen.go:156, internal/podmangen/podmangen.go:160)
- PARA-19: Every platform switch receives a value resolvePlatform has already validated against platformNames, and the runner and status switches fail loud in their default branches; the two silent defaults (instances.go:160-161, main.go:1291) are unreachable by construction. The project gates its platform-keyed maps (TestPlatformMapsCoverThreeNames) and has written no rule requiring switch exhaustiveness tests, so this stays a possible nice-to-have, not a defect. (see cmd/solmq-conn-util/main.go:55, cmd/solmq-conn-util/main.go:746, internal/runner/runner.go:471-472, internal/runner/runner.go:930-931, internal/runner/runner.go:993-994, cmd/solmq-conn-util/status.go:415-416, cmd/solmq-conn-util/main_test.go:508-511)
- SEC-01: command: flag VALUES are deliberately not inspected -- self-documented honest limitation (validate.go:1182-1184), and the userguide trust model (1140-1145) states env.yaml is executable configuration whose command: runs with your privileges and must be reviewed like a Makefile. Whoever authors kubernetes.command already controls image: and the whole deployment, so redirecting --server/--kubeconfig is within the documented trust surface. A minor hardening (reject known target-redirecting flags) is possible but not required. (see internal/validate/validate.go:1182-1184, docs/userguide.md:1140-1145)
- SEC-07: Host paths are charset-gated by safeHostPath (validate.go:900-911); accepting absolute and '..' paths and resolving relative ones against env.yaml is the documented, intentional behaviour (DEVELOPMENT.md:220-226, userguide trust model). The author choosing where their own deploy writes/bind-mounts is the trusted operator. Not a defect; the writing-location risk on a shared dir is covered narrowly by SEC-16. (see internal/validate/validate.go:900-911, docs/DEVELOPMENT.md:220-226)
- SEC-09: Once --allow-command bash is given, `bash -c reboot` passes because '-c' is flag-shaped and 'reboot' is treated as its value -- but --allow-command is an explicit, documented operator opt-in (userguide 1065-1069) and the flag-value limitation is self-documented (validate.go:1182-1184). The Windows PATHEXT/.bat re-parse angle (allowlist strips only .exe/.EXE, validate.go:1194-1202) is Windows-runtime-specific and could not be verified here -- recorded in gaps as suspected. (see internal/validate/validate.go:1225-1237, docs/userguide.md:1065-1069)
- SEC-10: applyCmdEnv does `cmd.Env = append(os.Environ(), c.Env...)`, which equals the OS default (a subprocess inherits the environment) plus the credential additions. kubectl/docker/podman require inherited env (KUBECONFIG, HOME, DOCKER_HOST). Not a defect. (see internal/runner/runner.go:336-342)
- SEC-11: Credentials traveling in the compose child's environment is the deliberate design of the compose environment-provider secrets model, chosen specifically to avoid writing secret values to disk; visibility via /proc/<pid>/environ or `ps e` is same-uid/root only and is pinned as intended by TestDeployDockerSeamChildEnvCarriesCredentials. Documented (UG 9.3). Minor doc gap: the Cmd.Env comment (runner.go:56-59) mentions only argv/file, not /proc visibility; not worth a separate finding. (see internal/runner/runner.go:56-59, cmd/solmq-conn-util/main_test.go:2504-2538, docs/userguide.md:1756-1760)
- SEC-13: A kubernetes Secret manifest with create: must carry the credential values -- that is what the operator applies; it is opt-in (create), written 0600 by emit() (main.go:1393), and UG 9.3 (1722-1755) explicitly tells operators to read stringData off the generated manifest. The 1614-1621 claim ('no value in any file this tool leaves on disk') is about the mounted config artifacts (application.yml/compose/quadlet), not the Secret object; no contradiction. (see cmd/solmq-conn-util/main.go:1388-1397, docs/userguide.md:1722-1755)
- SEC-15: Cred.Key() does embed 'L:'+literal, but it is used only as an in-memory map/comparison token; every operator-facing message uses Cred.Describe() (spec.go:347-357), which never prints the literal (e.g. validate.go:537,643). The comment's 'never exposes the literal value' holds in the sense that matters -- the token is never surfaced. Comment wording is slightly loose; not a defect. (see internal/spec/spec.go:347-357, internal/validate/validate.go:537,643)
